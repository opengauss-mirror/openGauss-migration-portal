# 1 架构总览

> 本章回答：这个项目是什么、用什么开发、怎么组织代码、能跑在哪里、为什么这样设计。读完应能建立起对 multidb-portal 的整体认知。

## 1.1 项目定位

multidb_portal 是一款基于 Java 开发的 **openGauss 数据迁移门户工具**，整合了 openGauss **全量迁移、增量迁移、反向迁移及数据校验**功能，支持完成 MySQL/PostgreSQL/Elasticsearch/Milvus 到 openGauss 的一站式迁移。

portal 本身不实现数据搬运，而是**编排层**：它驱动 5 类成熟迁移工具完成实际工作，并负责状态跟踪、进度展示与流程控制。

| 源数据库 | 全量迁移 | 全量数据校验 | 增量迁移 | 反向迁移 |
|---------|:---:|:---:|:---:|:---:|
| MySQL | ✅ | ✅ | ✅ | ✅ |
| PostgreSQL | ✅ | — | ✅ | ✅ |
| Elasticsearch | ✅ | — | — | — |
| Milvus | ✅ | — | — | — |

各阶段由以下工具承担：

| 迁移阶段 | 工具 |
|---------|------|
| 全量迁移 | chameleon（MySQL）、full_replicate（PostgreSQL）、milvus2datavec（Milvus）、elasticsearch2datavec（Elasticsearch） |
| 全量/增量数据校验 | openGauss-DataCheck（datachecker） |
| 增量迁移 | Debezium + Kafka Connect（MySQL、PostgreSQL） |
| 反向迁移 | Debezium + Kafka Connect（openGauss → MySQL/PostgreSQL） |

## 1.2 开发环境

| 项目 | 要求 | 说明 |
|------|------|------|
| JDK | **17** | `maven.compiler.source/target=17`（根 pom）；bin 脚本同样按 17 校验运行环境 |
| Maven | 3.x | 根 [pom.xml](../pom.xml) 聚合构建四个模块，无需单独构建子模块 |
| IDE | 任意 Java IDE | 推荐 IntelliJ IDEA；安装 Lombok 插件（代码大量使用） |
| 操作系统 | 开发/编码任意；**运行验证必须 Linux** | 见 1.4.2 |

构建命令与产物：

```bash
mvn clean package          # 在 multidb-portal 根目录执行
# 产物：portal-main/target/openGauss-portal-7.0.0.jar（uber-jar，唯一可执行产物）
```

关键三方依赖（版本统一管理在`pom.xml`）：

| 依赖 | 用途 |
|------|------|
| quarkus-bom | REST 服务框架（portal-quarkus） |
| lombok | 样板代码消除 |
| fastjson2 | 状态文件 JSON 序列化 |
| log4j2 | 日志 |
| commons-cli | CLI 命令解析 |
| opencsv | `status --detail` CSV 导出 |

| mysql-connector-j / postgresql | 源库连接 |
| milvus-sdk-java | Milvus 连接 |

## 1.3 Maven 模块划分

根 pom 以 `packaging=pom` 聚合四个模块，module 声明顺序即依赖自底向上：

```
multidb-portal/
├── portal-common      # 基础层：全局配置(Portal)、常量、枚举、异常、领域模型(TaskWorkspace)、工具类
├── portal-migration   # 引擎层：迁移编排(MigrationManager)、Job/Task/Provider、状态/进度、外部工具集成
├── portal-quarkus     # REST 层：Quarkus 常驻服务，HTTP 端点接收 CLI 控制指令
└── portal-main        # CLI 层：Main 入口、命令解析、命令/接收者，打包为可执行 uber-jar
```

依赖方向严格单向（上层依赖下层）：

```
portal-main → portal-quarkus → portal-migration → portal-common
```

## 1.4 运行环境约束

### 1.4.1 Java环境

- 运行环境需要 **Java 17 或更高版本**；
- 全部 bin 脚本（[task](../portal/bin/task)、[migration](../portal/bin/migration)、mode、install、uninstall）在执行前统一校验：`java` 在 PATH 中且版本 ≥ 17，否则报错退出（`Error: Java 17 or later is required`）；

### 1.4.2 操作系统

工具当前仅支持在指定系统架构的 **Linux 服务器**中运行，共 7 个平台（与安装包一一对应，见 build.sh 平台列表）：

| 系统名称 | 架构 |
|---------|------|
| CentOS7 | x86_64 |
| openEuler 20.03 | x86_64 / aarch64 |
| openEuler 22.03 | x86_64 / aarch64 |
| openEuler 24.03 | x86_64 / aarch64 |

**Windows 环境只能阅读和编译代码，无法完整运行迁移**——portal 大量使用 shell 命令安装和管理工具子进程，且各迁移工具本身均为 Linux 程序。

### 1.4.3 操作系统限制的原因

由于 Chameleon 是 Python 语言开发的工具，Chameleon 工具为了保证在上述操作系统安装的稳定性，对每个系统构建了虚拟环境并打包到了安装包中。portal 的安装包中包含 Chameleon 安装包，因此也有了系统架构的限制。

同理，pkg/ 目录下的其他工具（datachecker、Debezium/confluent 等）也按平台分发，安装包整体与操作系统绑定：**下载安装包时必须选择与服务器匹配的系统架构**。

### 1.4.4 磁盘空间

- portal 安装目录需预留 **至少 900MB** 可用空间（[PortalConstants.LEAST_SPACE_MB](../portal-common/src/main/java/org/opengauss/constants/PortalConstants.java#L66)）；
- 校验时机：`./bin/install tools` 安装迁移工具前，[InstallCommandReceiver](../portal-main/src/main/java/org/opengauss/command/receiver/InstallCommandReceiver.java#L174-L179) 检查 portal 根目录剩余空间，不足则抛出 `InstallException` 并终止安装；
- 空间主要用于 `tools/`（工具解压安装）与 `workspace/`（任务运行期数据与日志）。

## 1.5 安装包目录结构

安装包解压后得到 portal 目录，核心结构如下（[PortalConstants](../portal-common/src/main/java/org/opengauss/constants/PortalConstants.java) 定义全部目录名）：

```
portal/
├── openGauss-portal-7.0.0.jar     # 工具核心 jar（四个模块的聚合产物）
├── bin/                           # 工具操作命令目录：install/uninstall、task、migration、mode、kafka
├── config/                        # 工具配置目录：application.properties、log4j2.xml
├── pkg/                           # 迁移组件储存目录（未安装的工具包，按工具分子目录）
├── template/                      # 迁移模板文件储存目录（各工具配置模板，按工具分子目录）
├── workspace/                     # 迁移任务工作空间（每个任务一个 task_x 目录）
├── tools/                         # ./bin/install 后迁移工具的实际安装位置
├── data/                          # 自定义迁移模式 JSON 等运行数据
├── logs/                          # CLI 进程日志
└── tmp/                           # 临时文件（如 status --detail 导出的 CSV）
```

**注意：bin、config、jar、pkg、template 中的内容请勿修改删减，否则可能导致工具无法正常运行。**

## 1.6 关键设计决策

### 1.6.1 Quarkus常驻进程

迁移主进程是一个 **Quarkus REST 服务**：

- `migration start` 启动的 JVM 内嵌 Quarkus HTTP 服务
- 服务端口从 6000 起自动协商可用端口，写入任务目录的 `config/port` 文件；
- 服务常驻存活到迁移结束，期间持续执行迁移编排、监控子进程、刷新状态/进度文件；
- 好处：迁移过程中的任意时刻都能通过 HTTP 接收控制指令（停止增量、启动反向、查询健康状态等），**控制通道是主动的、双向的**，而非轮询文件。

### 1.6.2 CLI与迁移主进程分离

bin 目录的每个脚本执行都是一次**短命的 CLI 进程**（解析命令后即退出），与迁移主进程是两个独立 JVM：

- 唯一例外是 `migration start`：它启动的进程就是迁移主进程本身（Quarkus 常驻）；
- 其余控制类命令（stop、stop_incremental、start_reverse…）的路径是：CLI 读任务 `config/port` 文件 → 构造 `localhost:<port>` HTTP 请求 → 迁移主进程的 REST 端点执行 → CLI 输出结果退出；
- 状态查询类命令（task list、migration status）**不走 HTTP**，直接读取任务 `status/` 目录下的状态文件；
- 三道安全隔离：CLI 控制面与迁移数据面进程隔离；REST 端点仅绑定 localhost（三层本机校验，非本机请求 403）；CLI 与迁移进程之间无共享内存，全部通过端口文件、状态文件、心跳文件传递信息。

这个分离带来的直接收益：迁移主进程崩溃不影响 CLI 诊断（状态文件仍在）；CLI 误操作不会拖死迁移编排；多任务并行时每个任务一个独立 Quarkus 进程、互不干扰。

### 1.6.3 portal以子进程方式启动各迁移工具

portal 自身不搬运数据，chameleon、Debezium、datachecker 等工具全部作为**子进程**由 portal 启动和管理：

- 每个工具有独立的 `TaskProcess` 封装类（portal-migration 的 `process/task/`），统一负责：构造命令行 → ProcessBuilder 启动 → 日志重定向到任务 `logs/<阶段>/` 目录 → 等待退出/异步监控；
- **配置翻译**：用户只填写一份 `migration.properties`，portal 在启动工具前把它翻译成各工具的原生格式（chameleon 的 yml、Debezium 的 connector properties、datachecker 的 application-source/sink.yml），落盘到任务 `config/` 对应子目录；
- **生命周期托管**：`ProcessMonitor` 轮询感知全部迁移工具子进程存活情况；子进程异常退出时由 `ProcessErrorHandler` 决策（Kafka 异常会先尝试自动重启并恢复迁移，其余工具失败则中断迁移）；`migration stop` 时按阶段停止全部子进程；
- 工具的安装也由 portal 托管：`./bin/install <tool>` 把 `pkg/` 下的工具包解压安装到 `tools/`。

这层设计使 portal 保持"薄编排层"：替换某个底层工具（如换掉 datachecker）只需重写对应 Process/Task 类，不影响整体流程。

## 1.7 与旧版portal的关系

本仓库（openGauss-migration-portal）同时包含两代 portal：

| | 旧版（仓库根 `portal/`，PortalControl）                        | 新版（`multidb-portal/`，本文档对象） |
|---|--------------------------------------------------------|---|
| 定位 | "MySQL 一键式迁移"                                          | openGauss 数据迁移门户（多数据库） |
| 支持源库 | 仅 MySQL                                                | MySQL / PostgreSQL / Elasticsearch / Milvus |
| Maven 结构 | 单模块（`org.opengauss.portalcontroller`）                  | 四模块分层（见 1.3） |
| 核心入口 | PortalControl 单类驱动                                     | MigrationManager 编排 + Provider 工厂按源库分发 |
| 控制面 | 脚本 + 状态文件轮询                                            | CLI → Quarkus REST 主动控制（见 1.6.1/1.6.2） |
| 迁移模式 | Plan（代码内 Plan.java）                                    | mode 命令管理，JSON 存储，支持自定义模式 |

**延续性**（新版保留的旧版核心概念）：

- 工具栈一致：chameleon、Debezium/confluent、datachecker、full_replicate；
- 迁移阶段语义一致：全量 → 全量校验 → 增量 → 反向，含"增量与反向不能同时开启，需手动切换"的规则；
- 迁移模式思想一致：旧版 Plan 按顺序编排阶段，新版 mode 延续并扩展为可配置的模式体系。
